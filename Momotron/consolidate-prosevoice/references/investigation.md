## Question 1: Which momotron package and configuration patterns fit?

### What was inspected and observed

`momotron:pyproject.toml` uses Hatchling, Python >=3.12, a `momotron = momotron_lib.cli:main` console entrypoint, and packages `skills/momotron/scripts/momotron_lib`. It force-includes skill instructions, agents, schemas, templates, processes, assets and examples under `momotron_lib/_skill/` for wheel distribution. Runtime dependency is PyYAML; pytest, ruff and Playwright are development dependencies. These dependencies serve momotron's requirements, not prosevoice's.

`momotron:skills/momotron/scripts/momotron.py` is a thin PEP 723 launcher: it inserts its own script directory into `sys.path` and delegates to `momotron_lib.cli.main`. `momotron_lib/__init__.py:skill_root` locates `_skill/SKILL.md` when packaged and otherwise resolves from its module location. It does not derive assets from the working directory. `cli.py` centralizes argparse, JSON output and structured `MomoError` handling; verb modules register commands. Exit codes include workflow-specific states that prosevoice does not need.

`momotron_lib/config.py` resolves builtin < user < project < CLI. User config is `$XDG_CONFIG_HOME/momotron/config.json`, falling back to `~/.config/momotron/config.json`; project config is `<project>/.momotron/config.json`. Explicit project selection wins, then Git root, then the current directory. `Config` carries values, per-key provenance, configuration file paths and a project root. JSON duplicate keys and invalid types/unknown keys/schema versions are rejected; `schema.py` validates with handwritten Python, without a jsonschema dependency. Scalar and ordinary object settings are replaced at their tier; processes have special whole-entry replacement by ID. This is not a generic deep-merge system. User process paths are anchored to the user config directory, project paths to the project root, CLI paths to the caller's cwd. Templates resolve project > user > bundled by whole template directory. `init_project` creates support/config/cache directories without overwriting existing files and is idempotent; an existing `.gitignore` is left untouched, so its implementation alone does not guarantee an existing project ignores cache.

Ran direct configuration probes: CLI `plans_root` won over project and user; a user-only `max_review_cycles` retained user provenance; defaults retained builtin provenance. Duplicate JSON keys raised an error. Repeated initialization reported no new files. Source resource lookup found the reference skill directory. These are executed observations; wheel installation and external installer behavior were not exercised here.

### Proposal implications

Use one source tree `skills/prosevoice/`, a thin PEP 723 `scripts/prosevoice.py`, and `scripts/prosevoice_lib/` containing `cli`, `config`, `preflight`, `rules`, `artifacts`, `policy`, `harper`, `extract`, `premise`, `ready`, and `migration` responsibilities (modules can be combined where small). Use ordinary relative imports, one project/config resolver, and one resource-root function. The current source is stdlib-only with >=3.11 metadata; retain that requirement unless implementation establishes a reason to raise it. Do not copy PyYAML or momotron's workflow machinery merely to match its layout.

Add a Hatchling `pyproject.toml` with `prosevoice = prosevoice_lib.cli:main` and wheel package/resource inclusion matching the reference pattern. Include all agents, templates, bundled Harper policy, protocol and any schema data the runtime actually reads. Both `uv run <installed-skill>/scripts/prosevoice.py …` and the installed console command must work independently of cwd and the old sibling skills. A small explicit subcommand parser is sufficient; the decorator registry is optional, not a goal.

Recommended command coverage: `version`, `config`, `init`, `check`, `resolve`, `artifacts`, `rule`, `policy`, `lint`, `extract`, `premise`, `ready`, `migrate`. Consolidate seeding into an explicit initialization operation or retain a new `seed` subcommand if that keeps behavior clearer. Define a single JSON envelope and documented exit codes; preserve READY's clear/blocked/error distinction, but compatibility with old command syntax and old envelope shapes is not required. Update every caller atomically with the interface change.

Recommended new namespace: `.prosevoice/` in projects and `$XDG_CONFIG_HOME/prosevoice/` (fallback `~/.config/prosevoice/`) for user state. This is a design recommendation consistent with momotron, not a previously approved spelling decision. Use `schema_version: 1`, strict JSON validation, explicit `--project` and `--set`, and visible provenance. Reject legacy schema keys/locations in ordinary runtime discovery; only the migration command reads legacy state. User relative paths should be anchored to the user config directory, project paths to the project root, and CLI relative paths to cwd, with resolved paths included in diagnostics. State these rules in the schema/docs and test them.

Separate configuration precedence from guidance selection: merge guidance overrides per filename, replace each ordered candidate list as a unit at the winning tier, and then fall back independently to project and user guidance files. Preserve first-usable-file semantics and tried-path diagnostics. Do not accidentally replace a configured AUDIENCE list merely because a higher tier sets VOICE. Keep artifact location as a scalar choice. Dictionary and ignore-rule contents remain additive unions; they are not scalar settings. A project config should not discard user policy. Builtin templates are unfilled seed material, never fallback editorial guidance. Initialization must preserve existing guides/config and merge the cache ignore line idempotently, improving on momotron's existing-ignore limitation.

## Question 3: Which legacy layouts and migration contract?

### Observed supported legacy inputs

Current projects have optional `.prose-voice/config.json`, default VOICE/AUDIENCE/ILLUSTRATIONS files, dictionary.txt, ignore-rules.txt, `.gitignore` and `cache/<relative-directory>/<stem>.<kind>.md`. Older valid projects may have no config; adjacent sidecars are explicitly supported. Current user defaults live in `~/.prose-voice/` without a user config layer. Configured guide paths may be relative, absolute or tilde paths and point outside the project. Essay-local `.harper-words` and final assets are separate from this support directory.

Installed legacy skills may be under project/global `.claude/skills`, shared `.agents/skills`, or global `.config/opencode/skills`. Rules use `.claude/rules/PV-PROTOCOL.md` or exact `pv-protocol` managed blocks. The current helper also recognizes `.claude/rules/BLOG_VOICE.md` and `blog-voice` managed blocks. That is evidence for recognizing those rule remnants, not evidence for an undocumented older configuration schema. Unknown older layouts should be reported unsupported, not guessed.

A probe of `strip_block` with a missing END marker returned only text preceding BEGIN, deleting the trailing content from its return value. Migration must not reuse this permissive algorithm on malformed input. Ordinary rule refresh should share the safer parser once implemented.

### Recommended explicit interface and outputs

Use `prosevoice migrate --project <root>` as a read-only preview by default, and `--apply` for writes. Make user migration a separate explicit `--scope user` operation (or a separately authorized inclusion flag); support explicit legacy-user and new-user directory parameters for fixtures and controlled relocation. Respect XDG defaults for the new destination. Always report the complete read/write set. A project migration must not silently mutate global guides or global harness rules.

Return structured JSON with migration/schema version, selected roots/scope, `would-change`/`applied`/`unchanged`/`blocked` status, input hashes, each source/destination/action, translated config, external references, dependent user migration, conflicts, warnings, retained/skipped files and backup/journal paths. Use a nonzero result for blocked/unsupported states. Application should emit a durable manifest outside disposable cache (for example `.prosevoice/migrations/<id>/manifest.json`) and backups of replaced rule files. A no-op rerun must report no changes, not create repeated backup sets.

Translate old configuration explicitly into the new versioned schema, preserving ordered guidance paths and cache/adjacent mode. Rebase paths that point inside the moved support tree; retain external references and report their ownership rather than copying or editing external guidance. Preserve filled guidance bytes, policy files, custom ignore content and selected visual decisions. Convert the old unfilled-template marker to the new marker if the new format renames it; otherwise an unfilled guide could become usable by accident. The marker spelling itself need not change just because the entrypoint changes.

Copy known source guidance/policy into the new namespace and retain the legacy source as inactive recovery data until an explicit cleanup; do not offer legacy discovery in normal runtime. Report which source files remain and that old skill installs must be removed through the installer. Do not rewrite package-manager locks or delete shared symlink targets by guessing their format. Verify the new skill is installed before switching active rules, or report rule activation as a blocked prerequisite. Migrate recognized managed rules to a new prosevoice protocol name/marker while preserving all unrelated content. Recognize the evidenced BLOG_VOICE remnants only in the explicit migration path.

Preserve cache and adjacent behavior deliberately. Disposable reports may be left inactive and regenerated, but visual-selection sidecars can contain the only recorded choice for active anchors. Inventory anchored essays and preserve their selections: copy required illustration sidecars with link rebasing, or block with the exact regeneration/selection steps required. Never move essay sources, final assets or `.harper-words`. General report-history copying can be optional; when copying Markdown sidecars, account for relative links. If correct link rewriting cannot be established, leave the source intact and report a conflict rather than produce broken links. Adjacent sidecars should stay in place.

When a project relies on legacy global guides or dictionary/ignore policy, report that dependency. Require a separate explicit user migration (or specifically requested snapshot/import with recorded provenance) before claiming semantic equivalence. A project-only migration cannot claim success if it silently drops those effective inputs. This preserves scope boundaries without keeping implicit legacy runtime lookup.

### Conflicts, unsupported states and interruption

Preflight the entire operation before writes. Identical destination bytes or semantically equal generated config are no-ops; differing destination content blocks, with hashes and paths. Do not merge two competing voices or concatenate arbitrary configs. Duplicate JSON keys, unknown schema/keys, invalid types, unreadable sources, ambiguous essay-to-sidecar associations, malformed/duplicate/nested managed blocks, or unsafe symlink destinations produce actionable errors. Recognized default/source symlinks can be reported as external references; do not traverse writable destinations outside the selected scope. Unknown files inside the old directory are retained and listed for manual disposition; unknown configuration semantics are blocking.

Stage writes, record before/after hashes in the manifest, back up replaced rules, and use atomic per-file replacement. Multiple files are not a single atomic filesystem transaction: define a journaled resume rather than promise full atomicity. On re-run after interruption, accept only previously recorded completed writes whose hashes still match; continue pending writes when their expected inputs still match; otherwise block as a concurrent-edit conflict. Validate effective guidance, policy and artifact routing before activating new rules. Never delete old inputs before verifying the new state. An explicit rollback can restore only files still matching the migration's written hashes; otherwise provide manual recovery instructions. These are required design/test cases, not claims that such a helper already exists.
