# Migration contract

Implement this contract with the shared configuration/resource/policy layer in `contract.md`. Migration is the only runtime code allowed to read `.prose-voice` and legacy rule identities. Do not run it against real operator projects in this plan.

## Interface and scope

`prosevoice migrate --project ROOT [--apply]` defaults to project scope and read-only preview. `--scope user [--legacy-user-dir PATH] [--user-dir PATH]` explicitly selects user-only migration; defaults are `~/.prose-voice` to the XDG prosevoice directory. These relocation overrides are migration-only. Project migration must not write global guidance or rules; user migration must not rewrite project files. No force/overwrite or delete-legacy switch is provided. Preview performs full validation and writes nothing, including manifests, directories and cache.

Return the common envelope with data containing migration version, operation status (`would-change|applied|unchanged|blocked`), roots/scope, full read/write actions and input hashes, translated config, external references, dependencies, conflicts, warnings, retained/skipped paths, and manifest/backup locations. Blocked/unsupported operations exit nonzero. No-op reruns produce no new backup or manifest sets. Migration leaves all original legacy guidance/config/cache data intact and inactive; installation removal is an explicit installer task described to the operator, never a guessed lockfile edit or symlink deletion.

## Translation and semantic preservation

Support evidenced old project `.prose-voice` layouts with or without config and legacy user guides/policy. Strictly validate the actual old config schema, reject duplicate keys, and translate it to the new version. Preserve guide candidate ordering and artifact cache/adjacent mode. Map paths inside the legacy support tree to their new counterparts, preserving their referents under the new path-anchor rules. Retain external guide references and report ownership; do not copy or modify external files. Copy filled guides, dictionary/ignore policy and custom ignore content without content loss; retain the unfilled template marker. Unknown files stay at source and are listed, but unknown configuration semantics block.

Determine effective legacy guidance/policy dependencies before claiming equivalence. A project depending on old user defaults blocks until separate user migration establishes equivalent new inputs; report exactly what is missing. The migrator may inspect legacy user inputs for this comparison without acquiring authority to write them. User migration must retain user policy in the new directory even when projects supply their own guides. Verify equivalence of selected guide content, unioned policy and artifact mode through the new resolver before activating new rules.

Leave adjacent sidecars, essay sources, final assets and `.harper-words` untouched. Inventory essays and active visual anchors using the existing supported Markdown/sidecar conventions, including repeated essay stems in different directories. Copy required cache illustration decisions to the new cache routes and rebase relative Markdown links to the same targets. General disposable report history may stay inactive for regeneration; report that choice. Ambiguous essay/sidecar association, unsupported link rewriting or missing needed decisions blocks with exact remediation paths; never silently lose choices or report READY equivalence without checking its source/visual outcomes. The implementation need not become a general Markdown transformation engine: preserve recognized links and reject ambiguous cases.

Recognize only evidenced old `PV-PROTOCOL.md`, `BLOG_VOICE.md`, and exact `pv-protocol`/`blog-voice` managed block pairs, at supported harness targets. Confirm standalone legacy rule content is a recognized protocol before replacing it; unfamiliar modifications block for manual review. Reject missing/end-only/nested/duplicate markers before any writes. Replace recognized legacy active rules with the new protocol while retaining unrelated AGENTS content byte-for-byte. Verify a new `prosevoice` installation exists at the relevant target before switching rules; missing installations block with installer instructions. Do not remove legacy skill installations or alter installer locks. A malformed block must never truncate content.

## Conflicts and practical recovery

Preflight every input and destination before application. Identical destination bytes, or semantically identical generated config, are no-ops; differing content blocks with paths and expected/actual hashes. Reject unsafe destination symlinks and escapes from the selected scope; source symlinks are external references rather than permission to traverse/copy arbitrary trees. Unreadable sources, unsupported legacy formats and ambiguous mappings are actionable blockers. Blocked preflight writes no product state.

Use a small migration-specific manifest at `.prosevoice/migrations/<id>/manifest.json` (or user equivalent), outside disposable cache, containing planned actions, input/before/after hashes and completion state. Back up replaced rules in that directory. Stage changed bytes and atomically replace each destination; record intent before each write. Activate rules last, after shared-resolver verification. Do not claim multi-file atomicity or introduce a general transaction framework.

Re-running `--apply` detects an unfinished manifest. Match original input hashes, accept completed writes only if current bytes equal recorded after hashes, and continue pending writes only if their current state equals the recorded before state. Account for interruption between a replacement and marking it complete by accepting its recorded after hash. Any intervening edit blocks with the exact conflicting file and manifest path. Completed identical reruns do nothing. Provide concrete manual recovery instructions using retained sources and backups; restore or remove migration-written paths only after checking they still equal recorded after hashes. A rollback command is not required. Tests inject failures at representative boundaries, including before rule activation and after replacement but before completion recording.
